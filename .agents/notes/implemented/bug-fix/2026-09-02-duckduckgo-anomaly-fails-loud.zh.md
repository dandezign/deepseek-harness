# Agent Note：DuckDuckGo 异常响应以提供方错误呈现，而非空结果

Status: implemented

[English](2026-09-02-duckduckgo-anomaly-fails-loud.md) | 中文

## 问题

DuckDuckGo 对被限流或指纹被标记的客户端，返回一个承载于非 200 状态码之下的质询外壳（现网观测为 HTTP 202），而非报错。搜索工具把这个外壳当作普通响应解析，找不到任何结果链接，于是产出一个与合法空结果无法区分的产出，被封锁或限流的部署因此表现为"未找到结果"——模型看到的是正常回答，什么也没引用，会话记录和错误元数据都不携带封锁信息。

## 决策

`scripts/scrapling_tools.py` 在抓取后检查响应状态码：任何非 200 状态都返回一个指名状态码及其反爬/限流成因的领域错误产出，提供方既有的错误产出映射会把该消息原样以 `WEB_PROVIDER_ERROR` 呈现。HTTP 200 但解析为零结果的页面仍是诚实的空结果：确实无命中的查询是正常的，而 200 响应下的页面改版仍是包 README「已知局限」中记录的静默退化模式。

## 已考虑的替代方案

**只对 202 报错。** 否决：403、429 与 5xx 响应同样不含结果页；任何非 200 都意味着结果 HTML 不存在，一次状态码检查即可覆盖整个家族，无需维护一份封锁状态码清单。

**对所有空结果报错，包括 200。** 否决：无命中的查询是正常回答；把它们变成失败会让工具在窄查询上不可用，同时掩盖哪些查询确实没有结果。

**把被质询的搜索升级到 stealth 或 dynamic 抓取器。** 否决：静默地经由浏览器引擎重试，会把响亮的封锁变成缓慢的成功，成倍放大限流突发期间的资源开销，并加深恰好触发封锁的指纹压力。

## 验证

交换分类器 spec 通过 node fixture（`domain-error`）覆盖错误产出映射，`DSH_SCRAPLING_E2E` 套件覆盖真实端点；被封锁的部署会以携带状态码的 `WEB_PROVIDER_ERROR` 拒绝，而不是解析为空。

## 后果

被限流或被标记的部署会看到 `web_search` 以一个指名 HTTP 状态码的描述性错误失败，封锁因此可以从会话记录中诊断；空结果如今意味着端点以 200 应答且无可解析命中。区分硬封锁与瞬时限流仍需人工判断；错误消息同时点名两种成因。
