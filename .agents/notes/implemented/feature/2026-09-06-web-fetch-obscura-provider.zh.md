# Agent Note: Obscura 抓取提供方以状态探测保持 statusCode 真实

Status: implemented

[English](2026-09-06-web-fetch-obscura-provider.md) | 中文

## 问题

接缝的抓取契约报告被抓取资源的 HTTP 状态，`tool-web` 会把它渲染给模型（`Fetched <url> (HTTP <status>)`）。Obscura 头less浏览器是很有吸引力的自托管反检测抓取后端，但其渲染抓取路径对浏览器能显示的任何页面都以零退出——包括 4xx/5xx 错误页——且不暴露 HTTP 状态。只做渲染的抓取提供方就必须编造状态：404 错误页会以 HTTP 200 的标签到达模型。

## 决策

`web-fetch-obscura` 以 `obscura` 抓取提供方身份注册，每次抓取分两步执行：

1. **状态探测（建议性，默认 `statusProbe: true`）。** 通过 Obscura 的原始批处理路径发送一次请求（`fetch --quiet --file - --dump original --concurrency 1`，URL 走 stdin），它为每个 URL 打印一行携带真实 HTTP 状态的 JSON。提取状态时忽略该行的 `ok` 标志：`ok` 意味着 2xx/3xx，而 404 行恰恰是真实状态最重要的地方。非 2xx 页面仍会被渲染并作为携带真实状态的结果返回，与接缝“抓取到的非 2xx 资源是结果而非错误”的规则一致。
2. **渲染。** `fetch --quiet --dump <format>` 在 stdout 返回页面响应体（markdown/text/html）。

当探测无法作答——原始路径被封锁、超时、交换中断、行无法解析——成功的渲染报告 HTTP 200，因为引擎渲染出了一份确切状态无法证明的文档；该回退是文档化契约（README“抓取返回什么”），绝不是编造的错误状态。`statusProbe: false` 为时延敏感的部署跳过探测。探测绝不会让抓取失败：原始路径是反检测目标最先封锁的对象，而渲染器仍可能成功。运行时刻意保持无环境——可用性就是配置二进制上的一次 `existsSync`，每个操作都是全新的短命进程，`dsh-timeout` 的时限/中止机制与 stdout 大小上限均镜像 Scrapling 运行时的防护。

## 已考虑的替代方案

**对每次成功渲染都报告 200。** 否决：模型可见的输出不得说谎；模型依靠状态识别错误页，而最常见的情形（渲染良好的软 404 页）会悄悄误导它。

**通过 `--eval` 或页面内容从渲染中推导状态。** 否决：导航后的 JavaScript 看不到导航响应的 HTTP 状态；任何基于页面内容的启发式都比一次廉价的原始请求更糟。

**并行执行探测与渲染。** 延期：顺序执行让错误归属保持单一（渲染错误总是获胜），代价是一次快速的原始往返；本提供方针对缓慢的反检测页面，这点节省只是噪音。

## 验证

包测试套件覆盖：探测行解析（包括非 2xx 行与尾部噪音容忍）、针对内存脚本运行时的探测/渲染编排（真实 404 透传、探测失败时回退 200、跳过探测、html/text 响应体类型、截断、错误与中止分类、精确的 CLI argv 与 stdin）、覆盖 spawn/kill/超时/退出码路径的真实进程 fixture、经 `ctx.web` 的插件注册与自动选择，以及针对真实二进制、断言 example.com 以 HTTP 200 渲染且真实 404 报告 404 的环境门控 e2e——两者均在 Windows 上的 Obscura 0.2.2 实跑通过。

## 后果

部署在普通 HTTP 抓取器与付费托管抓取器之间获得自托管中间层。代价是每次抓取至多多一次原始请求（可跳过），以及原始路径被封锁而渲染通过时的文档化 200 回退窗口。预期的路由形态——HTTP，其次 Obscura，再次托管抓取器——仍在等待 web 服务中的提供方中立路由字段。
